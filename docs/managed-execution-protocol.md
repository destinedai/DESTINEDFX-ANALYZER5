# DestinedFX managed MT5 execution protocol (v1)

This protocol extends the existing HTTPS relay so a DestinedFX-operated Windows worker can provision and supervise an isolated MT5 terminal for an app user. The Android client must never connect to a broker with a generic TCP/WebSocket login or expose worker credentials. The worker runs the real MT5 terminal and EA; the relay is not a trading engine.

## Credentials and pairing

The app creates/retains a separate opaque application bearer through `POST /v1/pairings` for each local `DEMO` or `LIVE` profile. It submits `POST /v1/app/managed-account` with `{ "login":"123456", "server":"Broker-MT5", "password":"…", "access_type":"MASTER|INVESTOR", "account_mode":"DEMO|LIVE", "consent":true }` under that profile's bearer. App bearer tokens, profile credentials, pending command IDs, and authorization state are profile-scoped; they must not be reused across profiles. Investor access is read-only and MUST never authorize START. No broker credentials are returned from any subsequent API response.

The service requires `CREDENTIALS_FERNET_KEY` and `WORKER_TOKEN` at startup for managed-account endpoints; there is no plaintext fallback. It encrypts broker credentials at rest and exposes plaintext only in the authenticated, encrypted worker-claim response. Operator secrets are server-side only. Requests and logs must never include passwords or tokens.

Legacy records created before explicit profile mode was persisted are not automatically assigned to DEMO or LIVE. Their encrypted local values remain untouched, but the app does not load an unscoped token or pending command into either profile. Existing server records migrate as `UNVERIFIED` and must be explicitly revoked/re-enrolled under a selected profile before execution; do not infer a mode from the account number, server name, or a stale UI selection.

## Managed provisioning

`POST /v1/worker/jobs/claim` requires the operator-only worker bearer and `{ "worker_id":"…" }`. It atomically leases a queued job and returns `{ "job_id":"…", "kind":"PROVISION", "worker_id":"…", "pairing_id":"…", "pairing_code":"…", "bridge_url":"https://…", "account":{"login":"…","server":"…","password":"…","access_type":"MASTER|INVESTOR","account_mode":"DEMO|LIVE"} }`, or `{ "job":null }` when the queue is empty. Revocation jobs use `kind=REVOKE` and contain no credentials. A job is claimed at most once per lease. The worker writes expected login, exact server name, and profile mode into the EA configuration. The EA independently reads the actual terminal login/server and MT5 `ACCOUNT_TRADE_MODE`; it must match all three before claiming or executing. The worker provisions a user-isolated MT5 data directory, starts the terminal with its account settings and an auto-start EA profile, and deletes transient plaintext configuration files after launch where possible. Persisted terminal credentials still require encrypted host storage and restrictive per-user ACLs.

`PATCH /v1/worker/jobs/{job_id}` accepts `{ "worker_id":"…", "status":"PROVISIONING|AUTHENTICATING|FAILED|REVOKED", "error_code":"…", "error_message":"…" }`; worker IDs are bound to leases. `GET /v1/worker/jobs/{job_id}/status?worker_id=…` is operator-authenticated and lets the worker wait for completion. READY is set only after a fresh, account-matched EA heartbeat reports READY, terminal-connected, and a broker-reported account mode matching the profile; MASTER also needs broker trade permission. INVESTOR can be marked connected for read-only visibility, but remains ineligible for START. A terminal identity or account-mode mismatch clears the accepted heartbeat and LIVE authorization, and fails the provision job. A process launch alone never means READY. The app state response includes server-derived account identity verification, profile mode, access type, terminal freshness, authorization status/expiry, and sanitized error details.

## LIVE authorization

`POST /v1/app/live-authorization` requires `{ "confirm_live_trading":true }` from the authenticated app bearer for a LIVE, non-revoked MASTER profile. The bridge grants a 15-minute authorization only when the worker is READY and a fresh authenticated EA heartbeat verifies exact login, server, company, currency, and LIVE mode, with terminal connectivity and trade permission. `DELETE /v1/app/live-authorization` revokes it. Pairing revocation also clears the authorization. It is bound to the current pairing and exact login/server and never transfers to DEMO, another LIVE profile, or a different terminal identity. Re-authorization is required after expiry.

## Trading commands

Existing app command IDs remain UUID idempotency keys. The service rejects START and RESUME unless managed execution is READY, the EA heartbeat is fresh, the exact account identity and mode match the selected profile, the terminal reports connectivity and trade permission, and the profile is MASTER. LIVE additionally requires current explicit LIVE authorization; DEMO authorization state is separate. The Android client repeats these checks against fresh server state before queuing execution commands. The EA independently gates START, RESUME, and every order on its actual account identity/mode and its fresh accepted-heartbeat lease. STOP and EMERGENCY_STOP remain available to an authorized app even if the heartbeat is stale; these commands block new entries and do not silently close existing positions or alter broker-side SL/TP.

## Worker deployment requirements

The worker is Windows-only and requires a licensed/authorized MT5 terminal installation, the compiled `DestinedFXTraderEA.ex5`, outbound HTTPS to the relay and broker server access. Each account requires separate terminal data, logs, configuration and process supervision, protected with OS ACLs and encrypted storage. An operator must size host capacity, provision backups/monitoring, secure the TLS endpoint and set the credential-encryption and worker-authentication keys. The repo does not contain those secrets or a production endpoint.
