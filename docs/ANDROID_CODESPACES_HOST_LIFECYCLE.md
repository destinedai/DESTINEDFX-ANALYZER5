# Android START HOST / STOP HOST — GitHub App setup and safety contract

Updated: 2026-11-20

## Purpose and scope

The Android Bot workspace exposes separate START HOST / STOP HOST controls for the owner's GitHub Codespace. These controls are independent from the Bot's START, STOP, PAUSE, RESUME and EMERGENCY STOP commands.

The phone authorizes the actual GitHub user through GitHub App Device Flow, discovers the owner's Codespaces through GitHub, and selects only a Codespace whose repository and branch match:

- Repository: destinedai/DESTINEDFX-ANALYZER5
- Branch: free/phone-only-v1

The Codespace name is discovered from the API. It is never hard-coded.

## GitHub App configuration (owner action)

Create a GitHub App for DestinedFX in GitHub Developer settings.

1. Enable Device Flow under the GitHub App's user authorization settings.
2. Configure fine-grained repository permissions:
   - Codespaces: read — list the authenticated user's Codespaces and read selected Codespace details.
   - Codespaces lifecycle admin: write — start and stop the authenticated user's Codespaces.
3. Ensure the owner account can access the repository and Codespace.
4. Put the public GitHub App Client ID in Android build configuration as CODESPACES_GITHUB_CLIENT_ID (or enter the public Client ID in the host-control panel). The Client ID is not a secret.
5. For the optional server-side token revocation proxy, add CODESPACES_GITHUB_CLIENT_ID and CODESPACES_GITHUB_CLIENT_SECRET to the private GitHub Codespaces secret/environment configuration. Never put the App client secret in the APK, Android preferences, repository, Bridge logs, or chat.

The Android client uses GitHub REST API version `2026-03-10` and GitHub App Device Flow in a Custom Tab: it sends POST https://github.com/login/device/code and requests `offline_access`. GitHub's current guidance prefers authorization-code + PKCE for ordinary native apps and warns that Device Flow can be abused for phishing because it has no redirect URI. This implementation deliberately avoids shipping a GitHub App client secret in the APK and uses Device Flow because the phone must be able to authenticate and wake a Codespace while the Bridge is offline; GitHub explicitly permits refresh-token exchanges without the client secret when the original user token was generated by Device Flow. This is a documented security trade-off, not a claim that Device Flow is the strongest native-app flow. The app must open only the hard-coded `https://github.com/login/device` verification origin, show the one-time code, and tell the owner to enter it only on GitHub's genuine domain; users must never enter it into third-party sites or share it in chat. A stronger future design would require an always-available confidential token-exchange service or an approved PKCE-capable exchange path that still works while the Codespace is asleep; an App secret must not be moved into the APK. GitHub App user access tokens expire after eight hours; the refresh token expires after six months and rotates on use. Both tokens are stored in Android Keystore-backed encrypted preferences. A normal Actions `GITHUB_TOKEN` is not used to control a user's Codespace.

## START HOST sequence

1. Validate the saved GitHub App authorization or rotate the user token using its refresh token.
2. Discover Codespaces with GET /user/codespaces; filter by the exact repository and branch.
3. Fetch the chosen Codespace by its API-returned name and re-check repository/branch before any lifecycle request.
4. Enforce the local usage guard: block a new start when the estimated daily 90-minute target is used or estimated monthly core-hours remaining are below 10.
5. Request POST /user/codespaces/{name}/start and poll GitHub state until Available (or fail/deadline).
6. Report GitHub availability separately from Bridge, root host-agent, slot-isolation, MT5 terminal and fresh EA-heartbeat readiness. A Codespace marked Available is not proof that trading is ready.

The devcontainer postStartCommand invokes scripts/host/destinedfx_trigger_host.py start_all. That adapter reuses deploy/codespaces/host_controller.py, which owns deploy/codespaces/start.sh. It does not duplicate the MT5 launcher and does not call gui.sh (the owner-assisted installer wizard).

## STOP HOST sequence

1. The app shows explicit confirmation explaining that it inspects EA heartbeat, broker/account state, positions, pending orders, unresolved commands and backup integrity.
2. The app calls the owner-authenticated Bridge POST /v1/app/host/shutdown-safe (also available as POST /host/shutdown-safe). Bridge blocks new provisioning/commands, rejects unsafe or unknown broker state, and creates/rechecks an integrity-verified SQLite backup. It never liquidates or modifies positions/orders.
3. Before approval, the Bridge invokes the existing `deploy/codespaces/stop.sh --preflight`. This read-only command verifies DB/broker safety, isolated-slot manifests and root host-agent readiness. It returns an explicit `PASS: STOP PREFLIGHT acknowledged by stop.sh` only when checks pass. It does not stop any terminal, worker, Bridge or host process.
4. Only when Bridge returns `status=PREPARED`, `backup_verified=true`, `stop_script_ack=true` and `stop_script_status=PREFLIGHT_PASSED` does Android send GitHub POST /user/codespaces/{name}/stop. The full existing `stop.sh` cleanup still runs later through the Codespaces host supervisor as the Codespace shuts down, and it rechecks broker state before stopping isolated MT5 sessions.
5. The app polls Codespace state. If GitHub reports it still Available after a rejected stop, the app cancels the Bridge shutdown gate. If the result is ambiguous or GitHub reports Stopping/Shutdown, the app leaves the safety gate armed and asks the owner to verify state before another operation.
6. No Android STOP HOST action invokes the Bot STOP command. No automatic close-all, pending-order cancellation or trade liquidation is performed.

The host controller also exposes a separate idle_shutdown CLI operation. It rechecks broker state and a database backup, verifies the recorded supervisor PID/start-time/UID/executable/arguments, and delegates local service shutdown to the existing deploy/codespaces/stop.sh.

## Usage budget and limitations

GitHub's current plan documentation lists 120 Codespaces core-hours/month for personal GitHub Free accounts. Compute is billed as active wall time multiplied by the machine's core multiplier. A 2-core Codespace consumes two core-hours per wall-clock hour.

The owner target is 90 wall-clock minutes per day total, not 90 minutes of trading plus extra idle grace. At two cores, 90 minutes/day for 30 days is approximately 90 core-hours, leaving approximately 30 of the 120 core-hours as buffer. The target includes boot, active use, idle and shutdown time. The intended 20-minute idle period must be included within that 90-minute daily ceiling.

The Android app and host adapter maintain local estimates using recorded start/stop times and the known/assumed core count. These estimates are not GitHub's billing meter: the Android estimate is device-local, it cannot reconstruct time before tracking began on that device, and a forced stop/network loss can leave an unclosed estimate until the next reconciliation. GitHub reports billable compute hourly and exact billing-cycle usage must be checked at [GitHub Billing — Codespaces](https://github.com/settings/billing). The owner should also set the GitHub Codespaces idle timeout to 20 minutes in GitHub settings; the Bridge's own 20-minute idle setting is a separate application setting and does not change the account-level Codespaces idle timeout.

The usage display is deliberately labelled an estimate. It blocks new Android starts below the 10-core-hour monthly buffer and after the 90-minute daily target, but it cannot guarantee that GitHub will not bill for storage, other Codespaces, or additional usage from another device/session.

## Revocation

The REVOKE GITHUB APP action first tries the Bridge-side grant-revocation proxy. GitHub's app authorization grant-revocation endpoint requires Basic authentication using the GitHub App Client ID and client secret; the Bridge calls `DELETE /applications/{client_id}/grant` with the user's app access token. Therefore the APK never has that secret. Remote revocation is confirmed only when the configured Bridge proxy receives GitHub's successful response; then the app clears its local access and refresh tokens. If remote revocation fails, local token clearing is not reported as remote revocation.

If the Bridge does not have the two revocation settings configured or the proxy is unavailable, the app opens GitHub's application authorization settings for manual revocation. CLEAR DEVICE TOKEN only clears local device copies; it is not the same as revoking the GitHub App authorization remotely.

## Security and acceptance boundaries

- Codespaces API requests use the signed-in owner's GitHub App user token, not a repository-wide GITHUB_TOKEN or shared PAT.
- Codespace names are API-discovered and revalidated by repository and branch before start/stop.
- Broker credentials are sent only to the authenticated Bridge managed-account endpoint; they are never passed to GitHub API inputs.
- Codespaces remains EPHEMERAL and DEMO-only. The Linux Bridge rejects LIVE before credential persistence/job creation.
- Two-user Linux slot isolation still requires actual owner-host acceptance with two distinct DEMO pairings. Offline tests do not establish two real MT5 sessions.
- Physical Android installation, real FBS/Exness/HFM/Deriv DEMO account authentication and order lifecycle are still owner-side acceptance gates.
