# DestinedFX MT5 terminal bridge protocol (v1)

This protocol links the Android control app to an Expert Advisor running inside a logged-in MT5 desktop terminal/VPS. The bridge relays authenticated commands and telemetry; it never places broker orders itself. The EA obtains account identity, market data, trades, and trade results directly from its actual MT5 terminal. No MetaAPI token is used.

All public deployments MUST use HTTPS. A deployment must not expose HTTP except loopback-only development. Configure the bridge base URL in the Android setup screen and add the same exact base URL to MT5's **Tools → Options → Expert Advisors → Allow WebRequest for listed URL**. Do not use a placeholder host. The EA makes outbound HTTPS requests only.

## Pairing and credentials

`POST /v1/pairings` creates a single-use, short-lived pairing code and an Android app bearer token. Create a separate pairing for each DEMO or LIVE profile. Response: `{ "pairing_id": "…", "pairing_code": "…", "app_token": "…", "expires_at": "…" }`. The code expires after ten minutes and is consumed by one terminal claim. The app stores profile-scoped opaque app tokens only in Android encrypted preferences.

`POST /v1/terminal/claim` accepts `{ "pairing_code": "…", "terminal_instance_id": "…", "account": {"login":"…", "server":"…", "company":"…","currency":"…","account_mode":"DEMO|LIVE"} }`. The EA must derive account fields and mode from the running terminal, never trust user-entered account identity. The mode is read from MT5 `ACCOUNT_TRADE_MODE`; claim fails unless it matches the profile's requested mode. The worker-configured expected login and exact server are checked by the EA independently. Success returns `{ "terminal_id": "…", "terminal_token": "…", "poll_seconds": 2 }`. The EA retains the terminal token in its terminal-local persistent state and sends it as a bearer token. Tokens are random, unguessable, stored hashed at the bridge, never logged, and revocable by the app.

`DELETE /v1/app/pairing` revokes the app and terminal tokens for the paired terminal. It requires the app bearer token.

`POST /v1/app/live-authorization` accepts `{ "confirm_live_trading":true }` for a LIVE MASTER profile only after fresh terminal identity, mode, readiness, and trade-permission checks; it authorizes at most 15 minutes. `DELETE /v1/app/live-authorization` revokes that profile's current authorization. Pairing revocation and any terminal identity/mode mismatch clear it.

## App API

`GET /v1/app/state` requires the selected profile's app bearer token. Response includes terminal online/heartbeat age, EA state, the terminal's verified account identity and metrics, profile mode, positions, recent closed deals, last signal, and last error. It also includes server-derived `account_identity_verified` and `managed_execution` fields, including profile `account_mode`, access type, worker readiness, and current LIVE authorization/expiry. A missing or stale heartbeat is **OFFLINE**, never **RUNNING**.

The app-state response shape is `{ "pairing_status":"PAIRING|PAIRED", "terminal_online":true, "heartbeat_age_seconds":1, "heartbeat_stale_seconds":15, "ea_state":"READY", "terminal_connected":true, "trade_allowed":true, "account_identity_verified":true, "account":{ "login":"…", "server":"…", "company":"…", "currency":"…", "account_mode":"DEMO|LIVE", "balance":0, "equity":0, "margin":0, "free_margin":0, "margin_level":0, "leverage":0 }, "configuration":{…}, "last_signal":null, "last_error":"", "open_positions":[], "closed_deals":[], "last_heartbeat_at":"…", "last_command":null }`. The online flag and client freshness check use the server-configured stale threshold. Account is null until a valid terminal heartbeat. `last_command` is null or `{ "id":1, "request_id":"…", "action":"START", "status":"QUEUED|ACKNOWLEDGED", "outcome":"APPLIED|REJECTED", "state":"READY|RUNNING|PAUSED|STOPPED|ERROR", "message":"…" }`; outcome/state/message are omitted until the EA acknowledges. Position records contain `ticket`, `position_id`, `symbol`, `direction`, `volume`, `open_price`, `stop_loss`, `take_profit`, `floating_profit`, `commission` (number or null when unavailable), `swap`. Closed-deal records contain `ticket`, `position_id`, `symbol`, `closed_at`, `profit`, `commission`, `swap`.

The **terminal heartbeat request** is not an app-state response and must contain only `{ "state":"READY|RUNNING|PAUSED|STOPPED|ERROR", "timestamp":"ISO-8601 UTC", "terminal_connected":true, "trade_allowed":true, "account":{"login":"…","server":"…","company":"…","currency":"…","account_mode":"DEMO|LIVE",…}, "configuration":{…}, "last_signal":null, "last_error":"", "open_positions":[], "closed_deals":[] }`. The server derives `pairing_status`, identity verification, freshness, and online status; do not send app-only fields such as `ea_state`, `terminal_online`, or `heartbeat_age_seconds` in the heartbeat request. Mode or identity mismatch invalidates the last accepted heartbeat and LIVE authorization.

`POST /v1/app/commands` requires the selected profile's app bearer token and accepts `{ "request_id":"<UUID>", "action":"START|STOP|PAUSE|RESUME|EMERGENCY_STOP", "config": {"strategy":"ict-silver-bullet","symbols":["EURUSD"],"timeframes":["M5"],"risk_percent":0.25,"max_daily_loss_percent":2.0,"max_concurrent_positions":2} }`. `request_id` is an idempotency key. Repeating it with the identical payload returns the original command; reusing it with a different payload is rejected. START and RESUME require fresh server-verified profile identity/mode, READY worker and terminal, terminal connectivity/trade permission, MASTER access, and for LIVE a current explicit authorization. HTTP 202 means **queued only**, not applied or running. The app reports success only after fresh EA telemetry confirms the requested state. STOP/EMERGENCY_STOP prevent new entries; they do not close open positions or cancel orders. Existing SL/TP remain in place.

### Explicit destructive operations

The same authenticated command endpoint supports four distinct operations. Every request uses a new UUID and current profile bearer. Tickets are canonical positive base-10 integer strings; clients must not convert them through floating-point numbers. A selected order cancellation uses `CANCEL_PENDING_SELECTED` with `config: {"tickets":["<order-ticket>"]}`. Selected position closure uses `CLOSE_POSITION_SELECTED` with `config: {"tickets":["<position_id>"]}`. The bridge checks each selected identifier against the corresponding fresh, authenticated heartbeat for this pairing and rejects stale/offline identity, account-mode mismatches, revoked profiles, and non-MASTER/INVESTOR access. All requests expire quickly and are scoped to the bound terminal/account; a retry with a changed payload is rejected.

`CANCEL_EA_PENDING` takes no caller-supplied ticket list. The bridge snapshots only pending orders whose terminal heartbeat explicitly marks `managed_by_ea: true`, then sends that immutable ticket set to the EA. Unmarked/manual orders are never included. Empty snapshots are rejected rather than represented as a bulk cancellation.

`CLOSE_ALL` requires an additional explicit confirmation. First call `POST /v1/app/close-all-confirmation` with `{ "confirm_close_all": true }`; it returns a short-lived, single-use confirmation token bound to the current pairing, profile mode, login, and server. Submit that token with a fresh UUID and `CLOSE_ALL` plus the position IDs from the fresh snapshot. The bridge rejects expired, reused, or identity-mismatched confirmation tokens. The command contains a fixed server-derived target list; it must not silently expand to positions opened after confirmation.

Destructive command polling returns `tickets` and a UTC `expires_at`. Immediately before a broker call, the EA independently verifies the actual terminal account login/server/mode, current connectivity/trade permission, identifier membership, operation type, and expiration. The EA acknowledges ticket-scoped results using `results: [{"ticket":"<exact-target>","status":"APPLIED|REJECTED|UNKNOWN","message":"…"}]`. It must not report a requested target that it did not process, duplicate a ticket, or treat a CTrade call/HTTP response as broker confirmation. Bulk and partial outcomes remain per-ticket.

The bridge reports a destructive item as confirmed only after a **subsequent** fresh authenticated heartbeat from the same verified account establishes the resulting state: a cancelled order is absent from active pending orders, and a closed position ID is absent from open positions. An EA acknowledgement alone is provisional. Missing, stale, contradictory, timed-out, partially closed, or otherwise unresolved outcomes stay `UNKNOWN`/pending and are reconciled on later authenticated refreshes. A partial bulk result reports each item's independently reconciled status. No command may target another pairing, account, order, or position. Close operations preserve broker-side SL/TP on any remaining exposure; they do not imply changing protection.

## EA API

`GET /v1/terminal/commands?cursor=<integer>` requires the terminal bearer token. It returns `{ "cursor": n, "commands": [{"id":"…","request_id":"…","action":"…","config":{…}}] }`. Commands are retained and replayed until acknowledged. The EA must persist processed command IDs and apply each at most once.

`POST /v1/terminal/commands/{id}/ack` accepts `{ "outcome":"APPLIED|REJECTED", "state":"READY|RUNNING|PAUSED|STOPPED|ERROR", "message":"…" }` for lifecycle operations. Destructive commands additionally carry the per-ticket `results` array described above, with ticket values drawn only from that command's immutable target list. An acknowledgement of START alone does not establish RUNNING; a subsequent heartbeat must show the bot running and checks passing. An acknowledgement of a destructive operation alone likewise never establishes broker completion.

`POST /v1/terminal/heartbeat` requires the terminal bearer token and reports current state, UTC timestamp, terminal connectivity/trade permissions, actual `ACCOUNT_LOGIN` / server / company / currency, balance/equity/margin/free-margin/leverage, selected configuration and verified cost model, last signal/reason, active pending orders, open positions, recent realized deals including profit/commission/swap, and errors. `last_signal.execution_state` distinguishes accepted/submitted, partial and full fills, cancellation/rejection, position/SLTP reconciliation, closed-deal reconciliation, and unknown outcomes requiring reconciliation. Order and deal identifiers plus cumulative executed volume are authoritative; repeated telemetry is idempotently recomputed from broker history. The bridge rejects invalid, oversized, non-finite, mismatched-account, or stale data. The EA must not send passwords, broker API keys, or account credentials.

## Safety contract

EA state is authoritative for execution. START is allowed only after terminal/broker connection, trade permissions, fresh market data, valid account snapshot and risk configuration are confirmed. Max per-trade risk is 1% of `min(balance,equity)`; default is 0.25%. Minimum reward/risk is 2.0. Enforce broker tick size/value, volume step/min/max, stop distance, margin, duplicate-signal, daily-loss and concurrent-position limits in MQL5. STOP/PAUSE/EMERGENCY_STOP block new entries; existing positions retain their broker-side SL/TP. No retry may create a duplicate order.

The bridge is a relay/status service, not an MT5 terminal host. It requires separate deployment with a persistent database and HTTPS. The paired MT5 desktop terminal/VPS must remain online for the EA to trade. An Android phone alone cannot host an MQL5 EA. Source tests are not MetaEditor compilation; destructive operations must be accepted against a genuine DEMO terminal and reconciled with broker history before being described as broker-verified.

## Destructive-operation reconciliation details

The heartbeat contains all account open positions and pending orders. Position rows include both the current position `ticket` and stable `position_id`; close commands use `position_id`. Position and order rows include `managed_by_ea`, derived from the EA magic number, and current `volume` / `remaining_volume` respectively. Identifiers remain canonical decimal strings end-to-end.

The EA persists each request/ticket before a broker call and may update an initial `UNKNOWN` ticket result to `APPLIED` or `REJECTED` only after later terminal-history reconciliation. The bridge accepts those monotonic result upgrades and requires another fresh same-account heartbeat before operational confirmation. For cancellation, terminal-confirmed broker cancellation history plus the subsequent absence from active orders is required; disappearance alone is ambiguous because the order may have filled.

`GET /v1/app/state` exposes each destructive target's `ack_status`, `operational_status`, public `status`, `target_volume`, and `remaining_volume`. Public `PARTIAL` means a fresh heartbeat shows reduced but non-zero target volume; it is not final success, remains unresolved, and must remain visible in Android with the actual remaining volume. Only server-reconciled `APPLIED` or terminal `REJECTED` items are final. On app restart, the authenticated result list is sufficient to recover target IDs and resume reconciliation; a timeout never causes an automatic duplicate broker call.
