# Broker and Trading-Integration Research (2026)

**Research snapshot:** 2026-11-06
**Scope:** Official-source findings supplied for Deriv, OANDA v20, Exness, cTrader Open API, Interactive Brokers (IBKR), FBS, HFM, MetaTrader 5 transports, Android reliability, and trading UI.
**Interpretation:** This is a synthesis of the supplied research, not a validation of any particular application, account, credential, broker approval, or production deployment. “UNVERIFIED” means the supplied official-source research did not establish the claim; it must not be read as a definitive negative.

## Executive summary

The strongest documented direct integration paths in this research are Deriv, OANDA v20, cTrader Open API, and IBKR APIs, each with meaningful differences in auth, runtime, and account eligibility. Deriv’s official guidance supports OAuth for browser-facing apps and requires new app registration for the current APIs. OANDA’s API is token-authenticated and requires careful state reconciliation; its pricing stream is sampled rather than a complete tick history. cTrader provides OAuth plus separate application/account authorization and explicit demo/live endpoints, but broker enablement and safe retries still need validation. IBKR offers a socket API and a local Client Portal Gateway path; for individual accounts, operational/session constraints make OAuth an unproven shortcut.

Exness documents both a separate Exness API and a distinct MT5 terminal/Python route. Its official help page states the Exness API is currently available only in Vietnam and Thailand and that standard MT4/MT5 accounts cannot connect; Nigeria is outside the published API regions. Keep the API deferred and out of this app for the user's Nigeria account, while treating an owner-identified Exness MT5 DEMO account only through the separate managed MT5 path. FBS lists MT4/MT5 platforms and HFM documents MT5/MQL Expert Advisors; direct retail APIs for those brands remain unverified. MetaQuotes’ native EA and Python-to-terminal paths are documented; MetaApi is a third-party hosted option whose full pricing, independent security evidence, and authorization/compatibility remain unresolved.

Across all adapters, design for connectivity loss and ambiguous order outcomes. Android network availability is not proof of a healthy broker session, and Doze can interrupt background network access. The UI should distinguish local requests from broker-confirmed order states, show partial fills and stale data explicitly, and never imply a cancel or submission succeeded without authoritative confirmation.

## Findings by integration

### Deriv API

The documented REST base is `https://api.derivws.com`. REST calls use Bearer auth; PAT calls additionally require `Deriv-App-ID`, while OAuth bearer tokens do not require that header ([API overview](https://developers.deriv.com/docs/intro/api-overview/); [authentication](https://developers.deriv.com/docs/intro/authentication/), retrieved 2026-11-06). OAuth responses include `expires_in`; the docs say not to hardcode token lifetime and describe no refresh token. Reauthorize after the response’s expiry or a 401. The example value of 2,592,000 seconds is only an example, not a guaranteed lifetime ([OAuth](https://developers.deriv.com/docs/intro/oauth/), retrieved 2026-11-06).

For account-scoped authenticated WebSocket access, POST `/trading/v1/options/accounts/{accountId}/otp` with Bearer authorization and, for PAT, the app-ID header. OTPs are single-use and valid for 120 seconds; the response supplies a ready-to-use WebSocket URL. Authenticated demo/real paths and a public no-auth endpoint are documented ([Options WebSocket](https://developers.deriv.com/docs/options/websocket/); [Options](https://developers.deriv.com/docs/options/); [demo WebSocket](https://developers.deriv.com/docs/options/ws-demo/), retrieved 2026-11-06).

Legacy App IDs do not work with the new APIs; official workflows direct developers to register a new application ([workflows](https://developers.deriv.com/docs/workflows/), retrieved 2026-11-06). For browser-facing apps, the supplied recommendation is OAuth Authorization Code with PKCE, backend token exchange, exact HTTPS redirect allowlisting, minimal scopes, secure token storage, and expiry handling from each response. PAT is suggested by the official auth guidance where redirects are impractical, such as desktop/native/CLI contexts ([authentication](https://developers.deriv.com/docs/intro/authentication/), retrieved 2026-11-06).

Documented WebSocket budgets are grouped by call: proposal/proposal_open_contract/buy/sell 360 per minute and 14,400 per hour; balance/statement 100/2,000; portfolio/profit_table 30/1,500; all other calls 220/14,400. Ping is outside those budgets, capped at 10 per second per connection. REST limits are 300 requests/IP/minute, 1,000/IP/10 minutes, and 80/account/minute when logged in; Deriv reserves the right to change them ([limits](https://developers.deriv.com/docs/limits/), retrieved 2026-11-06).

Use one reusable WebSocket, periodic ping, exponential backoff with jitter, and after reconnect re-authenticate and restore subscriptions carefully. Authenticated reconnect requires a fresh OTP. Subscription IDs and `forget`/`forget_all` are documented; the docs do not promise a universal replay order or guarantee every subscription can be restored unchanged ([best practices](https://developers.deriv.com/docs/best-practices/); [workflows](https://developers.deriv.com/docs/workflows/), retrieved 2026-11-06). Production schemas are published in releases as WebSocket JSON Schemas and REST OpenAPI 3.1.0; the latest linked bundle is mutable, so pin and validate a release before implementation ([API overview](https://developers.deriv.com/docs/intro/api-overview/); [schemas release](https://github.com/deriv-com/deriv-api-schemas/releases/latest/download/schemas.zip), retrieved 2026-11-06).

**Priority:** High when Deriv is a confirmed target. Register a new App ID and test both auth branches, expiry/401 reauthorization, OTP timing/reuse, endpoint selection, limits, reconnect/resubscription, and compatibility against a pinned schema. These are validation recommendations, not a claim that an app has passed Deriv validation.

### OANDA v20

Official practice/live REST hosts are `api-fxpractice.oanda.com` and `api-fxtrade.oanda.com`; streaming hosts are `stream-fxpractice.oanda.com` and `stream-fxtrade.oanda.com`. Documented v3 paths include accounts, account details, orders, pricing, pricing stream, and transaction stream. Use matching environment hosts ([development guide](https://developer.oanda.com/rest-live-v20/development-guide/); [account](https://developer.oanda.com/rest-live-v20/account-ep/); [orders](https://developer.oanda.com/rest-live-v20/order-ep/); [pricing](https://developer.oanda.com/rest-live-v20/pricing-ep/); [transactions](https://developer.oanda.com/rest-live-v20/transaction-ep/), retrieved 2026-11-06).

A personal token is created in the fxTrade Account Management Portal after the API license agreement, can be revoked/regenerated, grants access to all subaccounts, and is sent as `Authorization: Bearer <token>`. OANDA says it does not retain a lost token; treat it like a password ([introduction](https://developer.oanda.com/rest-live-v20/introduction/); [authentication](https://developer.oanda.com/rest-live-v20/authentication/), retrieved 2026-11-06). Practice and live use their respective accounts/tokens. v20 accounts are available to all divisions except OANDA Global Markets and OANDA TMS BROKERS S.A.; other eligibility/account-variant questions remain unresolved ([development guide](https://developer.oanda.com/rest-live-v20/development-guide/); [introduction](https://developer.oanda.com/rest-live-v20/introduction/), retrieved 2026-11-06).

The pricing stream is sampled: at most four prices per second per instrument, reporting the price in effect at each 250 ms window’s end. Connection windows are not aligned, so clients can see different prices during rapid moves. Treat this as sampled state, not a complete tick/event history. `/pricing` supports `since` filtering ([pricing](https://developer.oanda.com/rest-live-v20/pricing-ep/), retrieved 2026-11-06).

For account reconciliation, initialize with Account Details, which supplies a consistent snapshot including pending orders, open trades, positions, and `lastTransactionID`. Then poll Account Updates from that transaction ID, apply `AccountChanges`, replace price-dependent `AccountState` fields, and persist the latest transaction ID ([best practices](https://developer.oanda.com/rest-live-v20/best-practices/); [account](https://developer.oanda.com/rest-live-v20/account-ep/), retrieved 2026-11-06). Order creation can return multiple related transaction IDs and conditional fill/cancel/reissue details; a 400 can include an order-reject transaction. Reconcile response and account/transaction state rather than treating HTTP success as proof an order remains open ([orders](https://developer.oanda.com/rest-live-v20/order-ep/), retrieved 2026-11-06).

**Reliability cautions:** The reviewed sources do not establish that `clientExtensions` are server-side idempotency keys; do not claim duplicate prevention. After transport failure, treat submission outcome as uncertain and reconcile before retrying. The transaction stream’s exact heartbeat cadence/payload, replay and resume guarantees are UNVERIFIED. A regional TMS-branded demo signup page is not universal onboarding evidence; guide users to their correct regional demo and confirm v20 practice-account access ([order definitions](https://developer.oanda.com/rest-live-v20/order-df/); [transaction stream](https://developer.oanda.com/rest-live-v20/transaction-ep/); [demo page](https://www.oanda.com/eu-en/demo-activate/a79be571de3242f3b4f7cdd74f78d5e6), retrieved 2026-11-06).

**Nigeria individual-retail eligibility:** OANDA's official group page assigns clients in “other countries” to OANDA Global Markets, while its v20 developer introduction explicitly excludes OANDA Global Markets and OANDA TMS Brokers S.A. from v20 account availability. The page describing countries accepted for partner traffic is not a retail-account eligibility list and does not establish API access. These sources do not confirm a Nigeria-resident individual retail v20 account; conservatively treat OANDA v20 as unavailable for this user unless OANDA confirms the user's specific legal entity and v20 DEMO account in writing. This is an evidence-limited assessment, not legal advice or a definitive statement that OANDA cannot accept a Nigerian customer ([OANDA coverage](https://www.oanda.com/group/where-we-are/); [v20 introduction](https://developer.oanda.com/rest-live-v20/introduction/); [partner traffic list](https://www.oanda.com/eu-en/partners-global/frequently-asked-questions/new-partners/which-countries-does-oanda-accept-traffic), retrieved 2026-11-06).

**Priority:** High if the user’s region/account is eligible. Default to practice, make environment selection explicit, discover accounts with `/v3/accounts`, securely handle tokens, reconcile by transaction ID, and do not retry ambiguous creates without checking authoritative state.

### Exness, FBS, and HFM

Exness's official Help Center article, updated 2026-09-29, documents a separate Exness API with REST and WebSocket trading/data functions, API key/secret setup, and an explicit availability restriction to **Vietnam and Thailand**. It also says standard MetaTrader accounts cannot connect. That public regional restriction excludes the user's Nigeria account for this product; no Exness API code is in Phase 1. Exness separately documents a terminal-mediated MT5/Python route ([Exness API Help Center](https://get.exness.help/hc/en-us/articles/27866287512476-Exness-API); [Exness MT5/Python](https://www.exness.com/blog/behind-the-markets/an-introduction-to-algorithmic-trading-with-python-and-mt5); [algorithmic trading](https://www.exness.com/indices/algorithmic-trading/), retrieved 2026-11-06).

The linked Exness developer portal documents signed `EXN-*` requests, Ed25519 signing, REST and WebSocket operations, asynchronous mutation acknowledgements, operation-status/history reconciliation, Gateway host selection, and account Access Point discovery ([developer overview](https://www.exness-api.com/); [Trader API reference](https://www.exness-api.com/reference/trading/exness-trader-api), retrieved 2026-11-06). The exact Access Point discovery operation path/schema is not identified in the retrieved Trader API OpenAPI paths; follow the current DNS widget/onboarding guide and do not hard-code the unverified legacy path. This API remains out of scope for Nigeria and no code is authorized. The separate MT5 route, if the owner's actual DEMO account is Exness MT5, must use the real terminal/account/server, not this API.

The FBS homepage lists MT4/MT5 platforms but does not document a direct API. HFM’s MT5 page documents MT5 and Expert Advisors using MQL, not a separate broker-owned REST, FIX, or WebSocket API ([FBS](https://fbs.com/); [HFM MT5](https://www.hfm.com/int/en/platforms/mt5), retrieved 2026-11-06). Direct retail API support for each remains **UNVERIFIED**, not a definitive negative. Obtain written official confirmation of availability, jurisdiction/account eligibility, credentials, endpoints, permissions, and terms before commitment. Do not treat MT5/EA support as evidence of a broker API.

**Priority:** Hold direct integration work for FBS/HFM and any non-MT5 Exness interface pending authoritative confirmation. Consider a platform-specific MT5 path only as a separately labeled design choice.

### cTrader Open API

The documented scopes are `accounts` (view-only information/statistics) and `trading` (account information/statistics plus permitted trading). Authorization codes expire after one minute. Access tokens last 2,628,000 seconds by default (about 30 days); refresh tokens remain valid until used to refresh or cTrader ID/trading accounts are re-authorized. Refreshing issues a new access/refresh pair and invalidates the old pair; refresh may occur before or after access-token expiry ([account authentication](https://help.ctrader.com/open-api/account-authentication/); [FAQ](https://help.ctrader.com/open-api/faq/), retrieved 2026-11-06).

Application registration/review and credentials are separate from user consent and account authorization. Exchange the user code at `https://openapi.ctrader.com/apps/token`, send application auth, retrieve authorized account IDs, then send per-account authorization. Newly created accounts require consent again ([application API](https://help.ctrader.com/open-api/api-application/); [account authentication](https://help.ctrader.com/open-api/account-authentication/), retrieved 2026-11-06).

Live/demo Protobuf endpoints are `live.ctraderapi.com:5035` and `demo.ctraderapi.com:5035`; JSON uses port 5036. Both TCP and WebSocket are supported; TCP requires SSL and WebSocket should be secure. Keep demo/live connections separate; docs recommend no more than two total (one each), heartbeat at least every 10 seconds, and serialized message handling. Python’s official SDK does not support WebSocket. Rate limits are 50 non-historical requests/second/connection and 5 historical/second/connection; excess may return 429 ([endpoints](https://help.ctrader.com/open-api/proxies-endpoints/); [connection](https://help.ctrader.com/open-api/connection/); [Protobuf](https://help.ctrader.com/open-api/sending-receiving-protobuf/); [overview](https://help.ctrader.com/open-api/), retrieved 2026-11-06).

**Reliability and eligibility:** cTrader-affiliated broker accounts are generally supported by default, but there is no complete broker allowlist or guarantee that every account is enabled. A complete reconnect/backoff/resubscription procedure and order idempotency/duplicate-suppression guarantees were not established. Treat disconnects and retries as potentially ambiguous; reconcile before retrying and verify target broker/account access ([overview](https://help.ctrader.com/open-api/); [messages](https://help.ctrader.com/open-api/messages/); [terms](https://help.ctrader.com/open-api/terms-of-use/), retrieved 2026-11-06).

**Priority:** High/medium when the target broker confirms access. Implement separate application and account auth, explicit trading consent, the correct endpoint/protocol, serialized messaging, heartbeat and throttling. Do not claim automatic recovery or idempotent execution.

### Interactive Brokers (IBKR)

TWS API is a TCP socket protocol to TWS or IB Gateway, with official libraries in several languages. Users install and configure the host, enable socket connections, and use documented default ports: TWS 7496 live/7497 paper; Gateway 4001 live/4002 paper. API trading is blocked by the default read-only setting. Gateway is smaller and API-focused but still requires host installation, configuration, process supervision, network/port management, updates, and writable settings ([TWS introduction](https://www.interactivebrokers.com/docs/tws-api/doc/introduction); [setup](https://www.interactivebrokers.com/campus/trading-lessons/installing-configuring-tws-for-the-api/), retrieved 2026-11-06).

Client Portal API uses HTTP through a local Java Gateway; current setup describes an IBKR Pro account and interactive login at `https://localhost:5000`. Gateway-mode sessions have significant constraints: browser authentication on the same machine, API calls from that machine, and one active brokerage/trading session per username. Other logins, including TWS, may interrupt or prevent Gateway operation ([installation/authentication](https://www.interactivebrokers.com/docs/web-api/authentication/cpgw/installation-authentication); [Gateway limitations](https://www.interactivebrokers.com/docs/web-api/authentication/cpgw/limitations-of-the-client-portal-gateway); [sessions](https://www.interactivebrokers.com/docs/web-api/authentication/sessions), retrieved 2026-11-06).

OAuth 1.0a/2.0 access is restricted to eligible licensed organizations, advisors, brokers, and third-party services; OAuth 2.0 is unavailable to Individual account structures and requires IBKR approval and a 3072-bit-or-greater RSA public key. Do not assume OAuth is a generic hosted alternative for an individual user ([OAuth 1.0a](https://www.interactivebrokers.com/docs/web-api/authentication/oauth-1a/introduction); [OAuth 2.0](https://www.interactivebrokers.com/docs/web-api/authentication/oauth-2/introduction); [registration](https://www.interactivebrokers.com/docs/web-api/authentication/oauth-2/register), retrieved 2026-11-06).

Forex contract/pair discovery is documented, but does not prove permissions, market data, or account eligibility for a user. Paper accounts require the user’s actual paper credentials and onboarding; anonymous “Try the Demo” API access and forex/API coverage are UNVERIFIED ([TWS contract](https://www.interactivebrokers.com/docs/tws-api/ref/contract); [currency pairs](https://www.interactivebrokers.com/docs/web-api/api-reference/trading/trading-contracts/get-currency-pairs); [paper auth](https://www.interactivebrokers.com/docs/web-api/authentication/paper), retrieved 2026-11-06).

**Priority:** For individuals, choose TWS/IB Gateway only if a continuously running workstation process is acceptable; choose Client Portal only if local Java Gateway and interactive single-session reauthentication are acceptable. Keep an adapter boundary, make paper/live explicit, and gate orders on verified permissions and account/session state. Do not plan around OAuth without confirmed eligibility.

### MetaTrader 5 transports and alternatives

MetaQuotes documents MQL5 Expert Advisors attached to charts and responding to terminal events, and a Python integration package that communicates with a running MT5 terminal via inter-process communication. MetaQuotes virtual hosting migrates a selected terminal environment (all, Experts, or Signals). ## Reliability findings and design implications

### Connectivity, mobile lifecycle, and orders

Android `NetworkCallback` reports network availability/loss/capability changes; it does not prove that a remote broker endpoint or WebSocket is healthy. Treat it as a reconnection hint and validate the application session ([connectivity status](https://developer.android.com/training/monitoring-device-state/connectivity-status-type); [NetworkCallback](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback), retrieved 2026-11-06).

Doze suspends network access and defers background work; Android recommends FCM over a separate persistent connection for downstream real-time messaging. Foreground services require a user-visible notification and are subject to background-start restrictions; they are not a blanket promise of continuous connectivity. Design for disconnect and reconcile on resume rather than assuming a persistent trading socket remains alive ([Doze](https://developer.android.com/training/monitoring-device-state/doze-standby); [background services](https://developer.android.com/develop/background-work/services); [FGS restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), retrieved 2026-11-06).

Use TLS with normal certificate and hostname validation. Android supports app/domain trust configuration and Keystore-protected non-exportable key material where available; neither solves session recovery or order replay. Use monotonic elapsed time for deadlines and heartbeat intervals because wall-clock time can jump ([networking](https://developer.android.com/develop/connectivity/network-ops/connecting); [security config](https://developer.android.com/privacy-and-security/security-config); [SSL](https://developer.android.com/training/articles/security-ssl); [Keystore](https://developer.android.com/privacy-and-security/keystore); [SystemClock](https://developer.android.com/reference/android/os/SystemClock), retrieved 2026-11-06).

A transport failure after sending an order creates an ambiguous outcome. Persist intent and request state, query authoritative order/execution state after reconnect, and reconcile before retry. Whether the selected backend supports idempotency keys or unique client order IDs, and what duplicate-submit behavior it guarantees, is **UNVERIFIED** until confirmed against that API contract. Apply this principle in combination with each broker’s specific limitations above.

### Order-state truthfulness and UI

IBKR’s documented states include Inactive, PendingSubmit, PreSubmitted, Submitted, Filled, PendingCancel, PreCancelled, Cancelled, and WarnState. PendingCancel/PreCancelled do not confirm cancellation; execution can still arrive while cancel is pending, and duplicate status messages may occur. Model requests-in-flight separately from acknowledged states, make updates idempotent, and show filled/remaining quantities ([IBKR order status](https://www.interactivebrokers.com/docs/tws-api/doc/order-management/order-status), retrieved 2026-11-06).

Other official retail help materials reinforce the same general caution without establishing universal broker behavior: Robinhood describes pending orders and review before cancel/replace ([help](https://robinhood.com/us/en/support/articles/cancel-a-pending-order/)); Fidelity notes that reaching a limit price does not assure execution, partial fills occur, and cancellation may be best-efforts ([FAQ](https://www.fidelity.com/trading/faqs-order-types)); Schwab describes status filters and expandable order details ([guide](https://www.schwab.com/content/how-to-check-order-status), retrieved 2026-11-06). Do not generalize one broker’s behavior to all others.

Practical UI synthesis:

- Make connection health, last update time, stale data, and recovery state explicit and text-labeled; do not rely on color alone.
- Separate review, submit, and broker acknowledgment. Show requested versus confirmed order state, partial-fill and remaining quantities, order parameters, and time-in-force/expiry where applicable.
- Treat cancel/replace as requests until confirmed; explain that execution may still arrive while cancellation is pending.
- Provide status-oriented filtering and progressive detail while keeping essential state visible.
- In Compose, use semantic theme tokens across light/dark schemes; maintain at least 4.5:1 text contrast for smaller text and 3:1 for other text, and 48dp minimum touch targets. ## Login-hardening addendum — 2026-11-06

The official Deriv authentication page explicitly presents two choices: OAuth 2.0 and PAT. It describes PAT as manual token entry and identifies desktop/native contexts as an appropriate PAT use case, while OAuth requires a redirect and authorization-code exchange. For this native Android phase, PAT remains the primary implemented flow; OAuth/PKCE remains a future option only if an app-link redirect, registered redirect URI, token-expiry handling, and an approved scope design are added and tested. PAT REST requests must include `Deriv-App-ID`; OAuth bearer requests do not. [1]

The Options WebSocket documentation confirms that `POST /trading/v1/options/accounts/{accountId}/otp` returns a ready-to-use authenticated URL. The OTP is single-use and valid for 120 seconds, and the endpoint requires the `trade` scope. A reconnect must therefore obtain a fresh OTP rather than reuse a previous URL. [2]

The published limits are now recorded as implementation constraints: REST is limited to 300 requests per IP per minute, 1,000 per IP per ten minutes, and 80 per logged-in user per minute. WebSocket budgets are grouped by operation, including 30 portfolio/profit-table requests per minute and 100 balance/statement requests per minute. The client must reuse a connection, avoid polling bursts, and back off after rejection. [3]

Android’s current security guidance recommends Android Keystore-backed key storage and states that API keys must not be committed to source control. Android’s connectivity guidance recommends `ConnectivityManager.NetworkCallback` for changes in default-network availability; this is only a reconnection hint and does not prove that Deriv is healthy. Doze suspends network access and defers background work, and foreground services are intended only for user-visible work with a notification. The app therefore treats a dropped socket as not-ready and requires a fresh broker synchronization before READY; it does not claim an always-on mobile session. [4] [5] [6] [7]

The implementation addendum adds deterministic, redacted failure mapping for invalid credentials/App ID, missing DEMO account, OTP expiry, rate limiting, network errors, and unavailable secure storage. It also adds `scripts/deriv_demo_smoke.py`, an owner-run read-only harness. It requests account list, account OTP, balance, portfolio, and one public tick only; it never invokes proposal, buy, sell, or order endpoints. No live broker session was run in this environment, and no credential was supplied.
