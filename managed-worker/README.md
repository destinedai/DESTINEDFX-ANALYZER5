# DestinedFX managed MT5 worker

This Windows-only worker consumes the managed execution API in `../docs/managed-execution-protocol.md`. It claims encrypted broker credentials using the operator-only bearer, stages and compiles the EA, writes a short-lived MT5 startup INI, and launches one isolated `/portable` terminal tree for that account. The worker never places trades itself or logs broker credentials. The control plane only reports READY after a fresh, account-matched EA heartbeat; MASTER additionally needs actual trade permission. INVESTOR sessions may be reported ready for read-only viewing but START is always rejected server-side.

Each queued job is bound to one DEMO or LIVE app profile and carries the expected login/server/mode into that account's EA `.set` file. The terminal must independently report the exact login, server, and `ACCOUNT_TRADE_MODE`; no profile may inherit another profile's pairing or LIVE authorization. The Android app requires a fresh, verified LIVE MASTER session and an explicit 15-minute authorization before START or RESUME.

## Prerequisites and configuration

Use Python 3.11 or later on a dedicated Windows Server host. Install a genuine broker-compatible MT5 terminal and MetaEditor. Configure `worker.example.toml` with the public HTTPS control-plane URL and absolute paths for the MT5 install, terminal executable, MetaEditor, approved EA source, and worker data root. Copy to a local `worker.toml`; it contains paths only and must not be committed. Supply `DESTINEDFX_WORKER_TOKEN` from the host secret store, never the command line or config file. Configure a stable unique `DESTINEDFX_WORKER_ID` in the Windows service environment; the worker refuses to start without it and never generates a replacement identity. This lets service restarts reconcile existing terminal markers and leases without bypassing ownership checks. Keep capacity to one provisioned account per worker/host unless the operator has deliberately tested and sized a multi-terminal host.

The control plane must have `BRIDGE_BASE_URL` set to its real public HTTPS origin, plus a Fernet-compatible `CREDENTIALS_FERNET_KEY` and strong `WORKER_TOKEN`. The app APK must be built with `MT5_MANAGED_SERVICE_URL` set to that same HTTPS origin. No worker token or encryption key belongs in Android or Git.

## Operation and security

Test the worker's cross-platform validation/configuration suite on Linux or Windows with:

```sh
python -m unittest -v
```

On Windows, run one cycle with `python worker.py --config worker.toml --once` or as a supervised Windows service with `python worker.py --config worker.toml`. The worker polls for queued jobs, reports PROVISIONING and AUTHENTICATING, and waits for the backend to confirm actual terminal heartbeat readiness or timeout. It persists a worker-owned marker containing the job, pairing, account directory, executable path, PID, and bounded restart count. Each cycle verifies the PID/executable identity, prevents duplicate terminals for a pairing, and may relaunch a crashed portable terminal up to `max_restart_retries` (default 3) with exponential `restart_backoff_seconds` (default 30); a restart never restores READY without a fresh authenticated EA heartbeat. Failed or timed-out dead trees are moved to a restricted `.quarantine` directory; a live or unverifiable process is left in place with operator-review status. It handles pairing revocation by stopping only the terminal PID recorded by the worker after verifying its executable path, then removes that account's local terminal tree. If ownership or termination cannot be verified, cleanup stops and requires operator review. Do not run two copies with the same worker ID.

Each account gets a separately copied MT5 installation and portable data directory; this consumes disk and RAM. Use a dedicated non-administrator service account, restrictive Windows ACLs, BitLocker/equivalent encrypted volumes, encrypted backups, process supervision, and tested recovery procedures. Python's POSIX mode bits are not a substitute for Windows ACLs. The MT5 startup INI contains the broker password in plaintext briefly and is deleted after terminal launch; MT5 may persist account authorization in its own data directory, which remains sensitive. Do not capture HTTP bodies, authorization headers, process arguments, or raw terminal logs without redaction.

## Limits and go-live checks

Restart markers preserve the non-secret login, exact server, DEMO/LIVE mode, MASTER/INVESTOR access type, bridge origin, optional claimed company/currency, executable identity, and explicit `startup_requires_start_command`/`webrequest_allowlist_required` state. Restart INIs never contain a password. MASTER restarts retain the terminal permission setting they require; INVESTOR restarts force `AllowLiveTrading=0`. The EA still starts in a safe non-trading state and must receive a fresh authenticated heartbeat before the bridge can report READY. MT5 WebRequest allowlisting is an operator step, not something the worker pretends to have configured.

The EA reports submitted orders, pending active orders, partial/actual executed volume, broker-confirmed positions, SL/TP, and closed deals separately. `TRADE_RETCODE_PLACED` is never presented as a fill. For risk sizing, `OBSERVED_ROUND_TURN` requires at least three same-symbol deal samples from the recent broker history; new accounts may use `CONFIGURED_ROUND_TURN` or `CONFIGURED_PER_SIDE` only with a positive operator-supplied cost and documented broker evidence. Unknown, missing, non-finite, negative, or unrepresentative costs block the trade rather than assuming zero or claiming a hard loss guarantee under slippage/gaps. Order identity and cumulative volume are persisted and reconciled against authoritative history after delayed fills, duplicate events, disconnection, and restart.

This environment does not include Windows, an MT5 terminal, MetaEditor, a production HTTPS service, or host credentials. The worker has only been tested with fake terminal/compiler executables on Linux; the EA has not been compiled here and no real or demo account has been authenticated. The lifecycle code is unit-testable but is not production-verified until exercised on the actual Windows host with the genuine terminal. A stale terminal heartbeat immediately disables new app START/RESUME commands, then receives a bounded recovery grace period measured from the stale transition rather than original job creation; a fresh account-matched heartbeat restores READY only through the current lease owner. A stale or ERROR state does not close existing positions. Test only with an authorized demo account until broker permissions, terminal lifecycle, order execution and failure recovery are independently verified.

## MT5 WebRequest allowlist

The worker writes the exact public HTTPS origin into the EA input `InpBridgeBaseURL`, but it does not claim to edit the terminal's **Tools → Options → Expert Advisors → Allow WebRequest for listed URL** allowlist. The operator must add the same origin manually in each isolated terminal (or use a separately verified broker/MetaTrader deployment mechanism) before startup. Successful process launch, EA compilation, or command queueing is not evidence of bridge connectivity; only a terminal claim followed by fresh authenticated heartbeat telemetry makes the worker job READY.

MetaQuotes documents `/config` startup with account login, server, password, and EA auto-start parameters; the official terminal is therefore technically automatable on Windows. This is distinct from MetaQuotes Virtual Hosting, which is rented/migrated through an MT5/MQL5 user workflow and cannot be assumed to be a free, centrally provisioned DestinedFX fleet. See the platform references in `../docs/mql5-platform-notes.md` and cost/setup notes in `../docs/managed-execution-operator-setup.md`.


## Quick-start worker kit

The GitHub Actions workflow publishes the DestinedFX-Windows-Worker-Kit artifact with the Python worker, sample config, EA source and launch-worker.ps1. Extract on Windows with the genuine broker MT5 desktop terminal and MetaEditor installed. The launcher prompts for the service URL and paths, reads the worker token through hidden input, and never writes the token into worker.toml. It runs in the foreground. MT5 WebRequest allowlisting is still a manual step. Running the worker process alone is not proof of account readiness.
