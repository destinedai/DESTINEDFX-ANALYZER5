# DestinedFX application-management backend

This is a standalone, broker-free FastAPI service for application accounts, sessions, user preferences, notification settings, minimal device registration, service health, and administrative audit reads. It does not connect to brokers, fetch brokerage balances, expose the MT5 bridge, or submit financial orders. The existing `bridge/` remains a separate owner-managed service and is not part of this stack.

## Supported deployment shape

`compose.yaml` defines one self-hosted Docker Compose stack: the API, private PostgreSQL 16, and Caddy HTTPS reverse proxy. PostgreSQL uses the named `postgres_data` volume; Caddy certificate state uses named volumes. The database and API are not published directly to the host. Only Caddy publishes ports 80/443. This is deployment configuration, not evidence that a host has been provisioned or this service is running.

Required owner-controlled settings are in `.env.example`. On a host with Docker Compose v2 and a domain you control:

1. Copy `.env.example` to `.env` in this directory. Generate an alphanumeric database password (for example `openssl rand -hex 32`) and replace **both** password placeholders. Replace `APP_DOMAIN` with a DNS name whose A/AAAA records point to the host and `CADDY_EMAIL` with an operator contact. Set `ADMIN_EMAILS` to the exact email address that will register the initial administrator. Never commit `.env`.
2. Check that Docker subnet `172.31.255.0/24` is not already used by the host or another Docker network. If it conflicts, change both `backend.compose.yaml` proxy network and the trusted proxy IP in the Dockerfile together.
3. Allow inbound TCP 80/443 and UDP 443 at the host firewall. Keep SSH access restricted. Caddy obtains and renews TLS certificates; certificate issuance requires working DNS and outbound internet.
4. Run `docker compose up --build -d`. API startup runs Alembic migrations before Uvicorn. Missing database, admin, or domain configuration fails Compose interpolation or startup; production configuration rejects non-PostgreSQL URLs.
5. Register the exact configured administrator email through `POST /api/v1/auth/register`. Registration is open by design in this initial version; rate limiting and strong password requirements apply. Review the initial account-creation policy before exposing the service broadly.
6. Verify `https://<APP_DOMAIN>/health` for process liveness, `/ready` for database readiness, and `/api/v1/service-status` for database-aware status. The app must not present the backend as online if readiness is unavailable.

Application API requests are versioned under `/api/v1`. OpenAPI JSON is generated by FastAPI at `/openapi.json`; interactive docs are disabled. Passwords are Argon2-hashed. The server returns an opaque random session token once at login and stores only its SHA-256 hash with expiration/revocation state. API clients must store the returned token in platform secure storage.

## Backups and restore verification

Keep backups outside the Compose host as well as on it, encrypt them at rest, and test restores periodically. From this directory, with Compose running and `.env` loaded by Compose:

```sh
set -a
. ./.env
set +a
umask 077
mkdir -p backups
stamp="$(date -u +%Y%m%dT%H%M%SZ)"
docker compose exec -T db pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom > "backups/app-management-${stamp}.dump"
sha256sum "backups/app-management-${stamp}.dump" > "backups/app-management-${stamp}.sha256"
```

For non-destructive restore verification, create a separate scratch database and restore there (never overwrite the live database as a test):

```sh
file="backups/app-management-<timestamp>.dump"
sha256sum --check "${file%.dump}.sha256"
docker compose exec -T db createdb -U "$POSTGRES_USER" restore_check
docker compose exec -T db pg_restore -U "$POSTGRES_USER" -d restore_check < "$file"
docker compose exec -T db psql -U "$POSTGRES_USER" -d restore_check -c '\\dt'
```

Record the result of restore checks and remove the scratch database after inspection. For an actual disaster recovery, stop API writes, restore into a separately verified database, update `DATABASE_URL` through the owner's secret-management process, then start the API and verify `/ready`, authenticated preferences, and audit access. This repository does not store backups or execute production restores.

## CI and verification boundary

`.github/workflows/build-apk.yml` includes a separate backend job with isolated unit/API/migration tests, a PostgreSQL service migration and persistence smoke test, Compose validation, image build, and dependency audit. A green job proves only its exact source revision in GitHub's test environment. It does not deploy a host, validate owner DNS/firewalls/backups, or provide production runtime evidence. No external deployment is claimed.

The API's in-memory rate limiter is process-local and resets on restart; operate a single API replica unless a shared rate-limit store is added. This initial backend does not yet implement user profile mutation, email verification, account recovery/deletion, config encryption, or multi-replica session/rate-limit coordination. Do not treat it as a finished public consumer identity platform until those product and security requirements are addressed.
